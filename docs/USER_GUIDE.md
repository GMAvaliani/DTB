## 1. Что такое цифровой двойник деятельности

Платформа отвечает на вопрос, на который не отвечают ни учётные системы, ни
средства бизнес-аналитики:

> **Что произойдёт с предприятием и с вероятностью достижения его целей, если
> при текущем состоянии, структуре деятельности, ресурсах и неопределённости
> внешней среды изменить управленческие решения?**

Учётная система фиксирует прошлое, аналитическая — показывает его в разрезах.
Цифровой двойник **проигрывает будущее**: многократно, с учётом случайных
событий внешней среды, и возвращает не одну цифру, а распределение исходов и
вероятность достижения каждой цели.

Практические следствия:

- решение об инвестиции в оборудование, найме персонала или принятии
  рискованного объёма заказов переводится из области интуиции в расчётную
  плоскость;
- узкие места выявляются **до** того, как проявятся в отчётности;
- альтернативные управленческие решения сравниваются количественно;
- любой полученный результат воспроизводим и потому проверяем.

### Что платформа не делает

Она не подменяет учётную систему и не ведёт первичный учёт. Учётная система
остаётся источником атомарных данных о ресурсах, персонале, оборудовании и
остатках; двойник надстраивает над ней макроуровень — модель деятельности,
которого в учётной системе нет.

## 2. Ключевые понятия

Модель строится из четырёх сущностей. Их немного намеренно: модель, которую
невозможно охватить взглядом, невозможно поддерживать в актуальном состоянии.

### Полезность

Любой результат деятельности — конечный или промежуточный. Совокупность
полезностей и их количеств образует **состояние предприятия** в каждый момент
времени.

Примеры: заказ клиента, партия сырья, комплектующие, готовое изделие,
оказанная услуга, перемещённый на склад запас, обученный сотрудник, денежные
средства, информация, выполненная работа.

Полезность — это не только материальный объект. Заказ и подписанный контракт —
такие же полезности, как изделие на складе.

### СЭД — структурный элемент деятельности

Единица деятельности, преобразующая одни полезности в другие. Каждый СЭД:

- потребляет **входные полезности** (в момент запуска);
- занимает **ресурсы** (на время выполнения);
- выполняется в течение некоторой (в общем случае случайной) длительности;
- формирует **выходные полезности** (в момент завершения).

Пример: «Производство» — заказ и 10 кг сырья на сборочной линии в течение
6–16 часов превращаются в готовое изделие.

СЭДы образуют иерархию произвольной глубины и в ходе моделирования ведут себя
как независимые агенты: каждый экземпляр СЭДа имеет собственное состояние и
реагирует на состояние предприятия и внешней среды.

### Ресурс

Возможность, которая **занимается** на время выполнения и затем
**освобождается**: сборочные линии, менеджеры, автопарк, финансовый лимит.

Различие с полезностью принципиально и определяет корректность модели:

| Признак | Полезность | Ресурс |
|---|---|---|
| Расходуется безвозвратно | да | нет |
| Возвращается после работы | нет | да |
| Примеры | сырьё, комплектующие, деньги | линия, оператор, автомобиль |

Сырьё, потраченное на изделие, — входная полезность. Станок, на котором это
изделие изготовлено, — ресурс.

### НП-событие (неопределённое или плановое)

Воздействие, порождающее деятельность или изменяющее условия её выполнения:

- **неопределённые**: поступление заказа, отказ оборудования, увольнение
  сотрудника, изменение регуляторных требований;
- **плановые и регламентные**: обслуживание оборудования, закрытие периода,
  инвентаризация, поставка по графику.

Неопределённые события задаются интенсивностью потока (например, 0,15 заказа в
час), плановые — расписанием или интервалом. Через события в модель входит
неопределённость, ради учёта которой и строится двойник.

### Причинно-следственная цепочка

Связанные между собой, эти элементы образуют цепочку, которая и делает модель
исполняемой:

```
НП-событие → СЭД → полезность → следующий СЭД → … → цель → KPI
```

Названия конкретных процессов («продажи», «производство») принадлежат вашей
модели, а не платформе: движок не содержит никаких предположений об отрасли.

### Модельное время

Всё время в платформе измеряется **в часах**. Момент `t = 0` — начало периода
моделирования («сейчас»). Отрицательные значения используются для исторических
данных (факт за прошлые периоды). Горизонт планирования задаётся для
предприятия и может переопределяться сценарием: 720 часов — это 30 суток.

## 3. Установка

### 3.1. Требования

- Python 3.11 или новее;
- 512 МБ оперативной памяти для типовых моделей;
- современный браузер (Chrome, Firefox, Edge, Safari);
- прав администратора не требуется, если используется виртуальное окружение.

Сборка фронтенда не нужна: интерфейс не имеет внешних зависимостей и
поставляется вместе с платформой.

### 3.2. Установка из репозитория

```bash
git clone -b claude/digital-twin-platform-7s4ywu https://github.com/GMAvaliani/DTB.git
cd DTB
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

Установятся зависимости: `pydantic`, `fastapi`, `uvicorn`, `sqlalchemy`,
`openpyxl`, `httpx`, `python-multipart`, а для разработки — `pytest`.

### 3.3. Проверка установки

```bash
dtb --help          # должен вывести список команд
python -m pytest    # 95 тестов, ~6 секунд
```

Успешное прохождение тестов означает, что корректно работают движок симуляции,
воспроизводимость расчётов, импорт/экспорт, API и полная приёмочная цепочка.

### 3.4. Запуск в Docker

```bash
docker build -t dtb .
docker run -p 8000:8000 -v dtb-data:/data dtb
```

Том `dtb-data` сохраняет базу данных между перезапусками контейнера.

### 3.5. Где хранятся данные

По умолчанию — файл `./data/dtb.db` (SQLite). Каталог задаётся переменной
`DTB_DATA_DIR`. Для промышленной эксплуатации указывается PostgreSQL:

```bash
export DTB_DATABASE_URL=postgresql://user:password@host:5432/dtb
```

Специфичных для SQLite конструкций в коде нет, миграция сводится к смене адреса
базы.

## 4. Первый запуск и демонстрационная модель

### 4.1. Запуск

```bash
dtb serve
```

Интерфейс открывается по адресу `http://localhost:8000`, спецификация
программного интерфейса — `http://localhost:8000/docs`.

Другой порт: `dtb serve --port 8080`. Доступ из сети: `dtb serve --host 0.0.0.0`.

### 4.2. Демонстрационная модель

Не начинайте с чистого листа. На экране **«Предприятия»** нажмите
**«Создать демо-модель „Демо-Завод“»** — будет создана полная модель
производственной компании и пять готовых сценариев.

Модель воспроизводит цепочку:

```
заказ клиента → продажи → планирование производства → производство →
контроль качества (ОТК) → приёмка на склад → доставка → получение оплаты
```

Дополнительно в неё входят: подготовка операторов, поставки материалов по
графику, отказы оборудования, регламентное обслуживание и увольнения
сотрудников как случайные события; 9 СЭДов, 12 полезностей, 7 ресурсов,
5 целей, 6 видов событий, 9 показателей.

Готовые сценарии:

| Сценарий | Содержание |
|---|---|
| Базовый | текущая структура деятельности без изменений |
| Рост спроса +40% | интенсивность потока заказов увеличена в 1,4 раза |
| Третья линия + рост спроса | инвестиция в оборудование при выросшем спросе |
| Стресс: отказы оборудования | утроенная интенсивность отказов и две аварии |
| Управление: скачок спроса | маркетинговая кампания с 240-го часа |

### 4.3. Пятиминутный тур

1. **«Модель предприятия»** — счётчики модели, результат валидации, качество
   данных и чек-лист рабочего процесса из 14 шагов с отметками выполненного.
2. **«Дерево целей»** — структура целей с показателями; щелчок по цели
   открывает её карточку.
3. **«СЭД / Полезности»** — причинно-следственный граф. Узлы перетаскиваются
   мышью, щелчок открывает свойства элемента, колесо мыши масштабирует.
4. **«Симуляция»** — выберите базовый сценарий, режим «Монте-Карло»,
   20 прогонов, и нажмите «Запустить». В мониторе видно модельное время, число
   наступивших событий, моменты переключения и размеры очередей.
5. **«Прогноз»** — постройте прогноз по базовому сценарию: вероятности
   достижения целей и коридор значений выручки.
6. **«Граф знаний»** — выберите узел «Сборочные линии» и нажмите «Влияние ↓»:
   платформа построит цепочки влияния до целей и показателей.

После этого логика платформы становится понятной, и можно переходить к
собственной модели.

## 5. Построение собственной модели: сквозной пример

Разберём построение модели на простом, но полном примере — столярная
мастерская, изготавливающая стулья на заказ. Все значения ниже проверены и
дают работающую модель.

**Логика примера:** поступает заказ → мастер изготавливает стул из досок →
стул продаётся, поступают деньги. Мастер один, поэтому при росте потока заказов
возникнет очередь — её и покажет расчёт.

### Шаг 1. Создать предприятие

Экран **«Предприятия»** → «Создать предприятие»:

```json
{
  "id": "workshop",
  "name": "Столярная мастерская",
  "description": "Изготовление стульев на заказ",
  "planning_horizon_hours": 500
}
```

Идентификатор `id` используется во всех связях, поэтому задавайте его
латиницей, кратко и осмысленно. Горизонт 500 часов — около трёх недель.

### Шаг 2. Описать полезности

Экран **«СЭД / Полезности»** → «Новая полезность». Создайте четыре:

```json
{"id": "request", "name": "Заявка клиента", "kind": "information", "unit": "шт"}
{"id": "timber",  "name": "Доска",          "kind": "material",    "unit": "шт"}
{"id": "chair",   "name": "Стул",           "kind": "product",     "unit": "шт"}
{"id": "cash",    "name": "Денежные средства", "kind": "money",    "unit": "руб"}
```

### Шаг 3. Задать показатель и цель

Сначала показатель (экран **«Дерево целей»** → «Добавить KPI»):

```json
{"id": "cash_in", "name": "Поступления", "expression": "produced('cash')", "unit": "руб"}
```

Затем цель:

```json
{
  "id": "g_cash",
  "name": "Заработать 150 000 за период",
  "target_metrics": [
    {"kpi_id": "cash_in", "target_value": 150000, "comparison": ">="}
  ]
}
```

Цель без измеримого показателя недостижима по определению — платформа сообщит
об этом при валидации.

### Шаг 4. Задать ресурс

Экран **«Ресурсы и оборудование»** → «Добавить ресурс»:

```json
{"id": "master", "name": "Мастер", "kind": "personnel", "capacity": 1, "unit": "чел"}
```

Ёмкость 1 означает, что одновременно может выполняться только одна работа,
требующая мастера.

### Шаг 5. Описать внешнюю среду

Экран **«События (НП)»** → «Добавить событие»:

```json
{
  "id": "client_request",
  "name": "Обращение клиента",
  "category": "external",
  "stream": {"kind": "poisson", "rate_per_hour": 0.15},
  "effects": [
    {"kind": "add_utility", "utility_type_id": "request", "quantity_expression": "1"}
  ]
}
```

Интенсивность 0,15 в час — примерно 3,6 заявки в сутки. Поток пуассоновский:
интервалы между заявками случайны, в среднем 6,7 часа. За 500 часов поступит
около 75 заявок.

### Шаг 6. Описать деятельность

Экран **«СЭД / Полезности»** → «Новый СЭД». Первый элемент — изготовление:

```json
{
  "id": "make",
  "name": "Изготовление",
  "goal_id": "g_cash",
  "inputs": [
    {"utility_type_id": "request", "quantity": 1},
    {"utility_type_id": "timber", "quantity": 3}
  ],
  "outputs": [{"utility_type_id": "chair", "quantity": 1}],
  "resources": [{"resource_id": "master", "quantity": 1}],
  "duration": {"kind": "triangular", "low": 5, "high": 15, "mode": 8},
  "triggers": [{"kind": "on_event", "event_kind_id": "client_request"}]
}
```

Второй — продажа, запускается автоматически по завершении изготовления:

```json
{
  "id": "sell",
  "name": "Продажа",
  "goal_id": "g_cash",
  "inputs": [{"utility_type_id": "chair", "quantity": 1}],
  "outputs": [{"utility_type_id": "cash", "quantity": 2500}],
  "duration": {"kind": "fixed", "value": 2},
  "triggers": [{"kind": "on_sed_completed", "sed_id": "make"}]
}
```

> **Рекомендация.** Длительность задавайте распределением, а не константой.
> «От 5 до 15 часов, чаще всего 8» отражает реальность точнее, чем «8 часов»,
> и именно вариативность порождает очереди и срывы сроков, которые вы хотите
> увидеть заранее.

### Шаг 7. Задать начальное состояние

Экран **«ERP-объекты и связи»** → «Начальное состояние» → «Редактировать»:

```json
{"utility_stocks": {"timber": 400}, "source": "manual"}
```

Четыреста досок — запас примерно на 133 стула, то есть материал заведомо не
будет ограничением: мы хотим увидеть влияние загрузки мастера, а не нехватки
досок.

### Шаг 8. Проверить модель

Откройте **«Модель предприятия»**. Должно отображаться «модель готова к
симуляции». Если есть критические ошибки — исправьте их, запуск расчёта будет
заблокирован.

### Шаг 9. Создать сценарий и запустить расчёт

Экран **«Сценарии»** → «Создать сценарий»:

```json
{
  "id": "ws_base",
  "name": "Базовый",
  "enterprise_id": "workshop",
  "seed": 42,
  "monte_carlo_runs": 20
}
```

Экран **«Симуляция»**: выберите сценарий, режим «Монте-Карло», 20 прогонов,
нажмите «Запустить».

### Шаг 10. Прочитать результат

На экране **«Прогноз»** вы увидите примерно следующее:

```
ожидаемые поступления      130 000 руб
коридор P5–P95             117 000 – 138 000 руб
вероятность достижения цели      0 %
```

Вывод однозначен: **цель в 150 000 рублей при текущей организации работы
недостижима** — ни в одном из смоделированных вариантов будущего она не
достигнута. Обратите внимание, что средний результат (130 тыс.) отстоит от цели
не так далеко, и «на глаз» ситуация могла бы показаться пограничной. Расчёт
показывает, что это не так.

Экран **«Результаты и таймлайн»** объясняет причину:

```
СЭД «Изготовление» ждал ресурс «Мастер» 8295 ч
Ресурс «Мастер» загружен на 99 % — критическая зависимость
Очередь к СЭД «Изготовление»: пик 32, не завершено 30
```

Мастер занят практически непрерывно, очередь заявок растёт в течение всего
периода, 30 заявок остались невыполненными к концу горизонта. Это и есть узкое
место — выявленное расчётом, с количественным обоснованием.

### Шаг 11. Проверить управленческую гипотезу

Окупится ли второй мастер? Экран **«Сценарии»** → «What-if» на базовом
сценарии:

```json
{
  "name": "Два мастера",
  "resource_capacity_overrides": {"master": 2}
}
```

Запустите расчёт по новому сценарию и откройте **«Сравнение сценариев»**:

| Вариант | Ожидаемые поступления | Вероятность достижения цели |
|---|---|---|
| Один мастер | 130 000 руб | 0 % |
| Два мастера | 181 000 руб | 95 % |

Прирост — 51 000 рублей за период, или 39 %. Теперь решение о найме второго
мастера сводится к сопоставлению этой величины с затратами на него, а
вероятность достижения цели выросла с нуля до практической определённости.

Это и есть типовой рабочий цикл: **модель → расчёт → узкое место → гипотеза →
количественное сравнение → решение.**

## 6. Справочник сущностей модели

Все сущности редактируются в интерфейсе как структуры JSON. Ниже перечислены
поля; необязательные можно не указывать.

### 6.1. Предприятие

| Поле | Описание |
|---|---|
| `id` | идентификатор (латиница, цифры, `_`, `-`) |
| `name`, `description` | наименование и описание |
| `planning_horizon_hours` | горизонт планирования в часах |
| `time_zone` | часовой пояс (справочно) |
| `simulation_calendar` | календарь; в текущей версии `24x7` |
| `model_version` | номер версии модели (увеличивается при сохранении снимка) |
| `status` | `draft` \| `active` \| `archived` |

### 6.2. Цель

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | идентификация |
| `parent_id` | родительская цель (иерархия) |
| `responsible_org_unit_id` | центр ответственности |
| `priority` | приоритет (меньше — важнее) |
| `target_metrics[]` | целевые показатели: `kpi_id`, `target_value`, `comparison` (`>=` или `<=`), `deadline_hours` (по умолчанию конец горизонта), `weight` |
| `sed_ids[]`, `resource_ids[]` | связанные элементы деятельности и ресурсы |
| `constraints[]` | ограничения-выражения |
| `valid_from`, `valid_to` | период действия цели |

### 6.3. Полезность

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | идентификация |
| `kind` | `product`, `service`, `component`, `material`, `raw_material`, `energy`, `money`, `information`, `work`, `trained_employee`, `moved_stock`, `other` |
| `unit` | единица измерения |
| `quality_attributes` | произвольные атрибуты качества |

### 6.4. СЭД

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | идентификация |
| `goal_id` | реализуемая цель |
| `parent_id` | родительский СЭД (иерархия произвольной глубины) |
| `org_unit_id` | исполняющее подразделение |
| `inputs[]` | входные полезности: `utility_type_id`, `quantity` |
| `outputs[]` | выходные полезности |
| `outcome_branches[]` | вероятностные исходы (см. ниже) |
| `resources[]` | требуемые ресурсы: `resource_id`, `quantity` |
| `equipment_ids[]` | используемое оборудование |
| `duration` | модель длительности (см. ниже) |
| `triggers[]` | условия запуска (см. ниже) |
| `start_condition` | дополнительное условие запуска (выражение) |
| `continuation_condition` | условие продолжения, проверяется в каждый момент переключения |
| `max_concurrent` | предельное число одновременно выполняемых экземпляров |
| `priority` | приоритет при конкуренции за входы и ресурсы (меньше — раньше) |
| `external_model` | подключение внешней модели: `uri`, `adapter`, `params`, `timeout_seconds` |

**Модели длительности** (`duration.kind` и требуемые параметры):

| Вид | Параметры | Применение |
|---|---|---|
| `fixed` | `value` | строго регламентированные операции |
| `uniform` | `low`, `high` | известны только границы |
| `triangular` | `low`, `high`, `mode` | известны границы и наиболее вероятное значение — **рекомендуется по умолчанию** |
| `normal` | `mean`, `std` | устойчивый процесс с симметричным разбросом |
| `lognormal` | `mean`, `std` | процессы с редкими длительными задержками |
| `exponential` | `mean` | процессы без «памяти» |

**Условия запуска** (`triggers[].kind`):

| Вид | Параметры | Смысл |
|---|---|---|
| `on_event` | `event_kind_id` | по наступлению события |
| `on_sed_completed` | `sed_id` | по завершении другого СЭДа |
| `at_time` | `at` | однократно в заданный момент |
| `recurring` | `interval`, `start` | периодически |

Дополнительно: `condition` — условие-фильтр (например, `branch == 'pass'`),
`count_expression` — число создаваемых экземпляров (по умолчанию `1`, может
зависеть от данных события, например `quantity`).

**Вероятностные исходы** применяются, когда результат работы не гарантирован:

```json
"outcome_branches": [
  {"label": "pass", "probability": 0.93,
   "outputs": [{"utility_type_id": "qc_passed_product", "quantity": 1}]},
  {"label": "fail", "probability": 0.07,
   "outputs": [{"utility_type_id": "defect_product", "quantity": 1}],
   "spawn_sed_ids": ["rework"]}
]
```

Здесь 7 % изделий признаются браком и автоматически направляются на доработку.

### 6.5. Ресурс

| Поле | Описание |
|---|---|
| `id`, `name` | идентификация |
| `kind` | `personnel`, `equipment`, `facility`, `vehicle`, `financial`, `energy`, `other` |
| `capacity` | ёмкость (сколько единиц работы может выполняться одновременно) |
| `unit` | единица измерения ёмкости |
| `org_unit_id` | принадлежность подразделению |
| `cost_per_hour` | стоимость часа (для стоимостных показателей) |

### 6.6. Организационная структура

**Подразделение**: `id`, `name`, `kind` (`enterprise`, `division`,
`department`, `team`, `responsibility_center`, `position`), `parent_id`,
`headcount_plan` (штатная численность).

**Сотрудник**: `id`, `name`, `org_unit_id`, `position`, `skills[]`,
`resource_id` — ресурсный пул, в который сотрудник вносит вклад.

**Оборудование**: `id`, `name`, `tech_place` (технологическое место),
`org_unit_id`, `resource_id`, `status`.

### 6.7. Событие

| Поле | Описание |
|---|---|
| `id`, `name`, `description` | идентификация |
| `category` | `external`, `internal`, `planned`, `regulatory`, `uncertain` |
| `stream` | модель потока (см. ниже) |
| `payload_defaults` | значения по умолчанию для данных события |
| `effects[]` | эффекты (см. ниже) |
| `affected_entity_ids[]` | затрагиваемые сущности (для графа знаний) |

**Модели потока** (`stream.kind`):

| Вид | Параметры | Смысл |
|---|---|---|
| `poisson` | `rate_per_hour` | простейший поток случайных событий |
| `scheduled` | `times[]` и/или `interval` + `start` | плановые и регламентные сроки |
| `external` | `external` (URI внешней модели) | поток рассчитывается внешней моделью |
| `none` | — | события поступают только из сценария |

**Эффекты события** (`effects[].kind`):

| Эффект | Параметры | Действие |
|---|---|---|
| `add_utility` | `utility_type_id`, `quantity_expression` | добавить полезность |
| `remove_utility` | `utility_type_id`, `quantity_expression` | изъять полезность |
| `spawn_sed` | `sed_id`, `quantity_expression` | создать экземпляры СЭДа |
| `resource_capacity_delta` | `resource_id`, `delta`, `duration` | изменить ёмкость ресурса; при указании `duration` — временно |
| `set_parameter` | `parameter_path`, `value` | изменить параметр модели |
| `cancel_sed_instances` | `sed_id` | отменить ожидающие экземпляры |

Любой эффект может иметь `condition` — условие применения.

Пример отказа оборудования на сутки:

```json
{"kind": "resource_capacity_delta", "resource_id": "production_line",
 "delta": -1, "duration": 24}
```

### 6.8. Показатель (KPI)

`id`, `name`, `unit`, `direction` (`maximize` или `minimize`) и `expression` —
выражение, вычисляемое по состоянию модели.

**Доступные функции:**

| Функция | Значение |
|---|---|
| `stock('u')` | текущий запас полезности |
| `produced('u')` | произведено за период нарастающим итогом |
| `consumed('u')` | потреблено за период |
| `completed('sed')` | число завершённых экземпляров СЭДа |
| `started('sed')` | число запущенных экземпляров |
| `events('kind')` | число наступивших событий вида |
| `utilization('res')` | загрузка ресурса (доля от 0 до 1) |
| `waiting_count('sed')` | текущее число ожидающих экземпляров |
| `executing_count('sed')` | текущее число выполняемых экземпляров |
| `t()` | текущее модельное время в часах |

Доступны арифметика, сравнения, логические операции, условное выражение
`a if cond else b` и функции `min`, `max`, `abs`, `round`, `floor`, `ceil`,
`sqrt`, `log`, `exp`.

Примеры:

```
produced('money')                                            выручка
100 * completed('delivery') / max(1, events('customer_order'))  уровень сервиса, %
completed('production_planning') - completed('delivery')     незавершённое производство
100 * produced('defect_product') / max(1, produced('finished_product'))  доля брака, %
```

Обратите внимание на приём `max(1, …)` в знаменателе — он защищает от деления
на ноль в начале расчёта.

### 7.4. Синтаксис ячеек

Чтобы не разносить модель по десяткам колонок, применяется компактная запись.

**Потоки полезностей** (`inputs`, `outputs`) и **ресурсы** (`resources`) —
через точку с запятой:

```
request:1; timber:3
master:1; truck:2
```

**Длительность** (`duration`):

```
fixed:4                   строго 4 часа
uniform:2..6              равномерно от 2 до 6
triangular:5..15@8        от 5 до 15, чаще всего 8
normal:5,1                среднее 5, стандартное отклонение 1
lognormal:1,0.5           логнормальное
exponential:5             показательное со средним 5
```

**Условия запуска** (`triggers`):

```
on_event:client_request           по наступлению события
on_sed_completed:make             по завершении другого СЭДа
at_time:5                         однократно на 5-м часу
recurring:168@40                  каждые 168 часов, начиная с 40-го
```

**Целевые показатели** (`targets` на листе целей):

```
cash_in:>=:30000              достичь 30 000 к концу горизонта
service_level:>=:75:360       достичь 75 % к 360-му часу
defect_rate:<=:10             не превысить 10 %
```

**Списки** (`sed_ids`, `equipment_ids`, `skills`, `times`) — через точку с
запятой: `line_1; line_2`.

**Сложные структуры** (`branches` на листе СЭДов, `effects` на листе событий) —
в формате JSON внутри ячейки:

```json
[{"kind": "add_utility", "utility_type_id": "request", "quantity_expression": "1"}]
```

### 7.5. Импорт CSV

Если удобнее работать с отдельными файлами, используйте импорт CSV: выберите
коллекцию (например, `seds`) и загрузите файл с теми же колонками. Разделитель
определяется автоматически, поддерживается кодировка UTF-8 (в том числе с BOM).

### 7.6. Импорт и экспорт JSON

Полная модель выгружается и загружается одним файлом JSON. Это удобно для
резервного копирования, переноса между средами и версионирования во внешней
системе контроля версий. Отдельно доступна выгрузка графа знаний в формате
Graph JSON.

## 8. Сценарии и анализ «что если»

### 8.1. Что такое сценарий

Сценарий — не копия модели, а **набор поправок к ней**. Базовая модель остаётся
неизменной, поэтому можно держать десятки вариантов будущего без риска её
испортить.

Сценарий может задавать:

| Поле | Что переопределяет |
|---|---|
| `horizon_hours` | горизонт моделирования |
| `seed` | значение генератора случайных чисел |
| `monte_carlo_runs` | число прогонов по умолчанию |
| `initial_stock_overrides` | начальные запасы полезностей |
| `event_rate_multipliers` | множители интенсивности потоков событий |
| `event_stream_overrides` | полная замена модели потока |
| `injected_events` | конкретные события в заданные моменты времени |
| `sed_overrides` | масштаб длительности, приоритет, предел параллелизма |
| `resource_capacity_overrides` | ёмкость ресурсов |
| `parameter_overrides` | произвольные параметры модели |
| `control_actions` | управляющие воздействия в заданные моменты |
| `objective` | целевая функция для оптимизации |

### 8.2. Создание варианта «что если»

На экране **«Сценарии»** нажмите «What-if» у нужного сценария и укажите только
то, что меняется:

```json
{
  "name": "Рост спроса на 40 % и третья линия",
  "event_rate_multipliers": {"customer_order": 1.4},
  "resource_capacity_overrides": {"production_line": 3}
}
```

Производный сценарий сохраняет ссылку на базовый — происхождение вариантов
видно в списке.

### 8.3. Управляющие воздействия

Управляющее воздействие — решение менеджмента, вводимое в конкретный момент
модельного времени. Например, маркетинговая кампания с 240-го часа,
повышающая интенсивность заказов:

```json
"control_actions": [
  {
    "time": 240,
    "label": "Маркетинговая кампания",
    "effect": {
      "kind": "set_parameter",
      "parameter_path": "event_kind:customer_order.stream.rate_per_hour",
      "value": 0.22
    }
  }
]
```

Пути параметров имеют вид `тип:идентификатор.поле`, например
`resource:production_line.capacity`, `sed:production.priority`.

### 8.4. Типовые вопросы, решаемые сценариями

| Управленческий вопрос | Что задать в сценарии |
|---|---|
| Выдержим ли рост спроса на 40 %? | `event_rate_multipliers` |
| Окупится ли третья линия? | `resource_capacity_overrides` |
| Что будет при серии отказов? | `event_rate_multipliers` + `injected_events` |
| Как повлияет ускорение операции на 20 %? | `sed_overrides` с `duration_scale: 0.8` |
| Хватит ли запаса материалов? | `initial_stock_overrides` |
| Когда вводить дополнительную смену? | `control_actions` |

## 9. Запуск симуляции

### 9.1. Как выполняется расчёт

Моделирование ведётся **в непрерывном модельном времени**. Платформа не
движется равномерным шагом, а определяет ближайший **момент переключения** —
очередное НП-событие, завершение выполняемого СЭДа, наступление планового срока
или введение управляющего воздействия — и переводит время сразу туда.

В этот момент:

1. отрабатывают эффекты наступивших событий;
2. порождённые СЭДы поступают в **пул ожидания**;
3. те из них, для которых доступны входные полезности и свободна требуемая
   ёмкость ресурсов, переводятся в **выполнение** — входы списываются сразу,
   результат появится по завершении;
4. для выполняемых СЭДов проверяется возможность продолжения: если событие
   отняло ресурс, СЭД **приостанавливается** и позднее доработает оставшуюся
   длительность;
5. время переводится к следующему моменту переключения.

Между двумя соседними моментами характер деятельности не меняется, поэтому
расчёт не тратится на «пустые» интервалы: месяц работы предприятия из
демонстрационной модели воспроизводится за 0,2 секунды.

### 9.2. Один прогон или серия

**Один прогон** — одна случайная реализация будущего. Он полезен для отладки
модели: видно поимённо, какой СЭД когда запустился и чего ждал. Принимать
решения по одному прогону нельзя.

**Монте-Карло** — серия прогонов с разными реализациями случайности. Даёт
ожидаемое значение, коридор P5–P95 и вероятность достижения целей. Именно этот
режим используется для управленческих выводов.

Рекомендации по числу прогонов: 20 — быстрая оценка, 50–100 — рабочая точность,
200 и более — если требуется устойчивая оценка вероятности редких исходов.

### 9.3. Значение random seed

Seed фиксирует последовательность случайных величин. Один и тот же seed при той
же модели и сценарии даёт **в точности** тот же результат. Это позволяет:

- воспроизвести любой опубликованный расчёт;
- сравнивать варианты решения на одинаковых реализациях случайности
  («общие случайные числа»), что резко повышает надёжность сравнения;
- разбирать конкретный неблагоприятный исход, не боясь его потерять.

Seed сохраняется в сведениях о происхождении каждого результата.

### 9.4. Ход расчёта

В мониторе отображаются: номер текущего прогона, модельное время, число
наступивших НП-событий, число моментов переключения, количество ожидающих и
выполняемых СЭДов. Расчёт можно поставить на паузу, продолжить или отменить —
на воспроизводимость это не влияет.

## 10. Чтение результатов

Экран **«Результаты и таймлайн»** показывает механику того, что происходило.

### 10.1. Итоговые показатели и достижение целей

Плитки с итоговыми значениями показателей и таблица достижения целей: по
каждой цели видно, достигнута ли она и с каким фактическим значением по
сравнению с целевым.

### 10.2. Траектории

**Траектория показателя** — как показатель изменялся во времени. Ступенчатый
характер линии естественен: значения меняются в моменты переключения.

**Пулы СЭД во времени** — сколько элементов деятельности ожидало и сколько
выполнялось. Это самый информативный график для диагностики:

- растущая линия ожидающих — узкое место, спрос превышает пропускную
  способность;
- «пила» с провалами до нуля — работа идёт рывками, вероятно, из-за
  неравномерных поставок или отказов;
- ровная линия выполняемых на уровне ёмкости ресурса — ресурс исчерпан.

### 10.3. Статистика элементов деятельности

По каждому СЭДу: создано, завершено, число приостановок, суммарные часы
ожидания, пиковый размер очереди, сколько экземпляров осталось незавершёнными.
Расхождение между «создано» и «завершено» — прямое указание на то, что система
не справляется с потоком.

### 10.4. Загрузка ресурсов

Доля времени, в течение которой ресурс был занят, суммарные часы занятости и
пиковое использование. Загрузка выше 85 % означает, что ресурс работает на
пределе: любое отклонение приведёт к росту очереди.

### 10.5. Узкие места

Перечень узких мест **вычисляется по трассе расчёта**, а не оценивается
экспертно, и содержит количественное обоснование:

```
СЭД «Производство» ждал ресурс «Сборочные линии» 1339.0 ч
Ресурс «Сборочные линии» загружен на 79 % — критическая зависимость
Очередь к СЭД «Производство»: пик 10, не завершено 5
СЭД «Производство» приостанавливался 7 раз (потеря ресурсов/условий)
```

Такие формулировки можно предъявлять в обоснование инвестиционного решения.

### 10.6. Журнал событий

Хронология: наступление НП-событий, создание, запуск, приостановка и завершение
экземпляров СЭДов, изменения ёмкости ресурсов, управляющие воздействия. Это
инструмент разбора конкретного прогона, когда результат кажется неожиданным.

## 11. Прогноз

Экран **«Прогноз»** — основной результат работы двойника.

### 11.1. Вероятность достижения целей

По каждой цели — вероятность достижения, а по каждому целевому показателю:
цель, ожидаемое значение, коридор P5–P95 и вероятность выполнения.

Интерпретация: 95 % означает, что в 19 из 20 смоделированных вариантов будущего
цель достигнута. Различие между 95 % и 60 % — это различие между рабочим планом
и планом, требующим управленческого вмешательства.

### 11.2. Факт, план и прогноз на одной диаграмме

Три линии в едином масштабе времени:

- **факт** — исторические значения, загруженные из учётной системы (слева от
  нуля);
- **план** — плановые значения;
- **прогноз** — ожидаемая траектория с доверительной полосой.

Полоса вокруг прогноза — коридор P5–P95: широкий коридор означает высокую
неопределённость, и решение, принятое по средней линии, может не подтвердиться.

### 11.3. Отклонение от плана и его причины

Платформа рассчитывает отклонение ожидаемого итога от плана и приводит
причины, ранжированные по значимости, — те же узкие места и цели под риском.
Это переход от констатации «план не выполняется» к ответу «потому что
производство простаивало 1339 часов в ожидании линий».

### 11.4. Влияние ресурсов

Таблица загрузки ресурсов с указанием ёмкости и пикового использования
показывает, какие именно ресурсы определяют результат.

## 12. Сравнение сценариев

Экран **«Сравнение сценариев»**: отметьте две или более завершённые симуляции —
первая отмеченная считается базой сравнения.

Результат:

- совмещённые траектории показателей;
- таблица итогов: ожидание, P5, P95, отклонение от базы в абсолютном и
  относительном выражении;
- изменение вероятности достижения каждой цели.

Корректность сравнения обеспечивается тем, что варианты просчитываются на
одинаковых реализациях случайности. Различие в результате объясняется
изменением решения, а не тем, что «одному сценарию повезло с заказами».

## 13. Оптимизация управленческих решений

Ручной перебор сценариев работает, пока вариантов немного. Оптимизация
автоматизирует поиск.

### 13.1. Постановка задачи

На экране **«Оптимизация»** задаются:

**Переменные решения** — что можно менять. Путь переменной определяет предмет
управления:

| Путь | Что варьируется |
|---|---|
| `resource:<id>` | ёмкость ресурса (оборудование, персонал) |
| `event_rate:<id>` | множитель интенсивности потока событий |
| `sed_duration:<id>` | масштаб длительности операции |
| `stock:<id>` | начальный запас полезности |
| `param:<тип>:<id>.<поле>` | произвольный параметр модели |

```json
[
  {"name": "lines", "path": "resource:production_line", "values": [2, 3, 4]},
  {"name": "trucks", "path": "resource:delivery_trucks", "values": [2, 3]}
]
```

**Целевая функция** — показатель и направление (максимизация или минимизация).
Не зашита в платформу: это может быть выручка, прибыль, денежный поток,
себестоимость, уровень сервиса, объём выпуска или произвольный показатель.

**Ограничения** — условия допустимости решения, по одному в строке:

```
kpi('service_level') >= 75
prob('g_production') >= 0.8
```

Здесь `kpi('id')` — ожидаемое итоговое значение показателя, `prob('goal_id')` —
вероятность достижения цели.

**Число прогонов на оценку** — сколько прогонов Монте-Карло выполняется для
каждого варианта. Меньше — быстрее, больше — надёжнее.

### 13.2. Как выполняется поиск

Каждый вариант оценивается серией прогонов Монте-Карло на **общих случайных
числах**: все варианты сталкиваются с одинаковыми реализациями случайности, что
устраняет ложные различия и позволяет сравнивать варианты корректно даже при
небольшом числе прогонов.

Результат: лучшее допустимое решение и полная таблица оценок — значение
целевой функции, признак допустимости и итоговые показатели по каждому
варианту. Таблица важна не меньше «лучшего» ответа: по ней видно, насколько
крут выигрыш и где наступает насыщение.

Пример из демонстрационной модели (число сборочных линий):

| Линий | Выручка | Загрузка линий |
|---|---|---|
| 2 | 2 160 000 | 76,9 % |
| 3 | 2 345 000 | 54,7 % |
| 4 | 2 400 000 | 41,0 % |

Переход от двух линий к трём даёт 185 тыс., от трёх к четырём — только 55 тыс.
при вдвое меньшей загрузке. Это и есть ответ о целесообразности инвестиции.

### 13.3. Методическое замечание

В основе — постановка задачи многошаговой оптимизации, где вектор состояния
формируется из параметров состояний СЭДов, а вектор управления — из
характеристик ресурсов. Аналитическое решение возможно лишь для сильно
агрегированных описаний, поэтому платформа использует алгоритмический подход:
оценку вариантов имитационным моделированием методом Монте-Карло. Архитектура
предусматривает подключение более сложных методов (динамическое
программирование по шагам переключения, стохастическая и эволюционная
оптимизация) через интерфейс подключаемых оптимизаторов.

## 14. Граф знаний и анализ влияния

Экран **«Граф знаний»** содержит все сущности двойника и связи между ними:
цели, элементы деятельности, полезности, ресурсы, подразделения, сотрудников,
оборудование, события, показатели и объекты учётной системы.

### 14.1. Навигация

- фильтры по типам сущностей — оставьте только интересующие;
- поиск по наименованию;
- перетаскивание узлов, масштабирование колесом мыши, перемещение полотна;
- щелчок по узлу открывает описание его связей.

Расположение узлов сохраняется между сеансами.

### 14.2. Анализ влияния

Кнопка **«Влияние ↓»** отвечает на вопрос: *что произойдёт, если изменить эту
сущность?* Платформа строит причинное замыкание вниз по потоку и показывает
цепочки:

```
Сборочные линии → Производство → Контроль качества (ОТК) → Приёмка на склад →
Доставка клиенту → Получение оплаты → Собрать выручку → Выручка
```

Кнопка **«Зависимости ↑»** отвечает на обратный вопрос: *от чего зависит
достижение этой цели?*

Практическое применение: перед изменением модели — оценка последствий; при
разборе отклонения — поиск первопричины; при обсуждении с коллегами —
наглядная демонстрация того, как ресурс влияет на финансовый результат.

## 15. Валидация модели и качество данных

### 15.1. Валидация — обязательный контроль перед расчётом

Проверяются: ссылки на несуществующие сущности, циклы в иерархиях, циклы
нулевой длительности без условий выхода, корректность выражений, недостижимые
цели, отсутствующие ресурсы, отрицательные количества, события без обработчиков,
элементы деятельности без входов или выходов.

Замечания делятся на три уровня:

| Уровень | Влияние |
|---|---|
| Критическое | **расчёт заблокирован** |
| Предупреждение | расчёт возможен, но результат может быть не тем, что вы ожидаете |
| Информационное | справочно |

Блокировка при критических ошибках — осознанное ограничение: расчёт по
некорректной модели опаснее отсутствия расчёта, поскольку выглядит достоверно.

### 15.2. Качество данных

Отдельный отчёт с интегральной оценкой: пропущенные значения, дубликаты
наименований, разорванные ссылки, несогласованные единицы измерения,
невозможные состояния, изолированные сущности, противоречивые связи с учётной
системой, нарушенный порядок временных рядов.

Для цифрового двойника качество данных критично: модель, построенная на
противоречивых данных, даёт уверенно выглядящий, но неверный прогноз.

## 16. Версии модели и журнал изменений

### 16.1. Версии

Экран **«Версии модели»** → «Сохранить текущую версию» создаёт снимок с
комментарием, автором и хешем содержимого. Любые две версии сравниваются
построчно: что добавлено, что удалено, какие поля изменились и с какого
значения на какое.

Сохраняйте версию перед существенными изменениями и после завершения этапа
работы. Через полгода вы должны понимать, на какой именно модели был получен
опубликованный прогноз.

### 16.2. Журнал изменений

Фиксирует, кто, что и когда изменил: создание и удаление сущностей, импорт
данных, запуск расчётов, сохранение версий.

### 16.3. Происхождение результата

Каждый результат расчёта содержит: идентификатор предприятия, версию и хеш
модели, сценарий и его версию, хеш начального состояния, значение random seed,
горизонт, версию движка и отметку времени. Этого достаточно, чтобы повторить
расчёт в точности.

## 17. Интеграция с учётными системами

### 17.1. Принцип

Учётная система — источник атомарных данных. Конвейер:

```
учётная система → коннектор → нормализация → модель двойника
```

Платформа не ведёт первичный учёт и не подменяет ERP.

### 17.2. Что загружается

| Тип объекта | Куда попадает |
|---|---|
| `material_stock` | начальные запасы полезностей |
| `employee` | сотрудники |
| `equipment` | оборудование |
| `org_unit` | подразделения |
| `kpi_actual` | фактические значения показателей |

Нераспознанные типы сохраняются как объекты учётной системы и остаются
доступными для связывания вручную. Ссылки на неописанные в модели полезности
и показатели не создаются автоматически — вместо этого выдаётся
предупреждение: модель деятельности проектируется человеком, а не выводится из
данных.

Каждый загруженный объект связывается с сущностью модели (вид 8), что позволяет
проследить, откуда получено каждое значение.

### 17.3. Доступные коннекторы

- **демонстрационный коннектор** — реалистичный набор данных, проходящий через
  настоящий конвейер нормализации; служит для освоения и тестирования;
- **универсальный REST-коннектор** — настраиваемое соответствие «тип объекта →
  адрес выгрузки», авторизация заголовками, преобразование имён полей;
- **импорт Excel, CSV и JSON** — когда прямой доступ к системе невозможен.

Адаптеры к конкретным учётным системам (1С, «Галактика», MES, WMS) реализуют
тот же интерфейс; в текущей версии реализован интерфейс, конкретные адаптеры
вынесены в план развития.

## 18. Работа из командной строки

```bash
dtb serve [--host 0.0.0.0] [--port 8000] [--reload]
```
Запуск интерфейса и программного интерфейса.

```bash
dtb demo
```
Создание демонстрационного предприятия и пяти сценариев.

```bash
dtb simulate <идентификатор_сценария> [--runs N] [--seed S]
```
Расчёт. Без `--runs` выполняется один прогон и выводится результат с полными
сведениями о происхождении; при `--runs N` — Монте-Карло с итоговой
статистикой и вероятностями достижения целей. Вывод в формате JSON пригоден
для передачи по конвейеру в другие инструменты.

```bash
dtb validate <идентификатор_предприятия>
```
Проверка модели и отчёт о качестве данных.

```bash
dtb export-template <файл.xlsx>
```
Выгрузка пустого шаблона Excel для описания модели.

Пример: сравнение двух сценариев без интерфейса —

```bash
dtb simulate demo_baseline --runs 50 > baseline.json
dtb simulate demo_extra_line --runs 50 > extra_line.json
```

## 19. Программный интерфейс (REST API)

Полный функционал доступен через REST API, что позволяет встроить расчёты в
существующие процессы планирования. Интерактивная спецификация — по адресу
`/docs` работающего сервера. Основные группы:

| Назначение | Точки входа |
|---|---|
| Предприятия и модель | `/api/enterprises`, `/api/enterprises/{id}/model`, `/api/enterprises/{id}/entities/{тип}` |
| Валидация и качество | `/api/enterprises/{id}/validation`, `/api/enterprises/{id}/data-quality` |
| Версии | `/api/enterprises/{id}/versions`, `/api/enterprises/{id}/versions-diff` |
| Граф знаний | `/api/enterprises/{id}/graph`, `.../graph/impact/{узел}`, `.../graph/dependencies/{узел}` |
| Сценарии | `/api/scenarios`, `/api/scenarios/{id}/whatif` |
| Симуляции | `/api/simulations`, `.../state`, `.../timeline`, `.../events`, `.../bottlenecks`, `.../stream` |
| Прогноз | `/api/forecasts`, `/api/forecasts/deviations` |
| Оптимизация | `/api/optimizations` |
| Импорт и экспорт | `/api/enterprises/{id}/import/...`, `/api/enterprises/{id}/export/...` |
| Журнал | `/api/audit` |

Расчёты запускаются асинхронно: вызов возвращает идентификатор задания, ход
выполнения передаётся потоком событий (`/stream`) или опросом состояния.

## 20. Конфигурация и эксплуатация

### 20.1. Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `DTB_DATABASE_URL` | адрес базы данных | `sqlite:///./data/dtb.db` |
| `DTB_DATA_DIR` | каталог данных для SQLite | `./data` |
| `DTB_API_KEYS` | ключи доступа и роли | не задано — открытый режим разработки |
| `DTB_EXTERNAL_MODEL_HOSTS` | список разрешённых узлов для внешних моделей | не задано — любой адрес http(s) |
| `DTB_FRONTEND_DIR` | каталог статики интерфейса | определяется автоматически |

### 20.2. Разграничение доступа

Формат ключей: `ключ:роль[:идентификатор_предприятия]`, через запятую.

```bash
export DTB_API_KEYS="k-adm:admin,k-analyst:editor,k-view:viewer,k-div:editor:division_a"
```

| Роль | Права |
|---|---|
| `viewer` | просмотр модели, результатов, прогнозов |
| `editor` | изменение модели, сценариев, запуск расчётов |
| `admin` | дополнительно удаление предприятий |

Ключ с указанием предприятия ограничивает доступ только этим предприятием —
изоляция подразделений или клиентов. Если переменная не задана, платформа
работает в открытом режиме и сообщает об этом при запуске.

### 20.3. Безопасность внешних моделей

Отдельные элементы деятельности могут рассчитываться внешними моделями,
вызываемыми по адресу URI. Разрешены только протоколы http и https, действуют
тайм-ауты, а `DTB_EXTERNAL_MODEL_HOSTS` ограничивает список допустимых узлов.
Платформа никогда не исполняет код, поступивший вместе с данными модели.

### 20.4. Промышленная эксплуатация

```bash
export DTB_DATABASE_URL=postgresql://dtb:пароль@db-host:5432/dtb
export DTB_API_KEYS="..."
dtb serve --host 0.0.0.0 --port 8000
```

Платформа представляет собой обычное ASGI-приложение и разворачивается за
обратным прокси-сервером (nginx) с завершением TLS. Резервное копирование —
штатными средствами используемой СУБД; дополнительно рекомендуется выгружать
модели в JSON.

## 21. Диагностика типичных проблем

**Симуляция не запускается, возвращается сообщение о валидации.**
В модели есть критические ошибки. Откройте «Модель предприятия» и исправьте
замечания уровня «critical» — как правило, это ссылка на несуществующую
сущность.

**Элемент деятельности ни разу не выполнился.**
Возможные причины: не задан триггер (проверьте предупреждение
«СЭД не имеет триггеров»); никогда не выполнялись условия запуска; не хватало
входных полезностей — посмотрите в «Результатах» столбец часов ожидания и
причину блокировки.

**Очередь растёт неограниченно.**
Интенсивность входного потока превышает пропускную способность. Сравните
среднее время между событиями (1/интенсивность) со средней длительностью
операции, делённой на ёмкость ресурса. Раздел «Узкие места» укажет ресурс.

**Все прогоны Монте-Карло дают одинаковый результат.**
В модели нет источников случайности: все длительности заданы как `fixed`, а все
потоки — как `scheduled`. Задайте распределения длительностей и пуассоновские
потоки там, где неопределённость реальна.

**Результат отличается от полученного вчера.**
Проверьте seed, версию модели и параметры сценария — все они входят в сведения
о происхождении результата. При совпадении этих величин результат совпадает
побитово.

**Полезность потребляется, но никогда не производится.**
Отчёт о качестве данных отметит это как ошибку. Добавьте производящий элемент
деятельности, событие поставки или начальный запас.

**Импорт Excel завершился с ошибками.**
Отчёт указывает лист и номер строки. Наиболее частые причины: пустой `id`,
ссылка на несуществующий идентификатор, неверный формат длительности или
триггера. Модель при ошибках не сохраняется — исправьте файл и повторите
загрузку.

**Порт занят.**
`dtb serve --port 8080`.

**Интерфейс не открывается, программный интерфейс работает.**
Укажите путь к статике: `export DTB_FRONTEND_DIR=/путь/к/DTB/frontend`.

**Расчёт идёт слишком долго.**
Сократите число прогонов или горизонт для отладки, а полную серию запускайте
после того, как модель стабилизировалась. Учтите, что время расчёта растёт с
числом событий и экземпляров элементов деятельности, а не с длиной горизонта
как таковой.

## 22. Глоссарий

**Полезность** — любой результат деятельности, конечный или промежуточный;
совокупность полезностей описывает состояние предприятия.

**СЭД (структурный элемент деятельности)** — единица деятельности,
преобразующая входные полезности в выходные с использованием ресурсов;
в ходе моделирования ведёт себя как агент.

**Ресурс** — возможность, занимаемая на время выполнения и затем
освобождаемая, в отличие от безвозвратно расходуемой полезности.

**НП-событие** — неопределённое или плановое событие внешней среды либо
внутренней жизни предприятия, порождающее деятельность или изменяющее условия
её выполнения.

**Момент переключения (МП)** — момент модельного времени, в который наступает
НП-событие, завершается элемент деятельности либо вводится управляющее
воздействие. Между соседними моментами переключения характер деятельности не
меняется.

**Сценарий** — набор поправок к модели, описывающий один вариант будущего:
изменённые потоки событий, ёмкости ресурсов, параметры деятельности и
управляющие воздействия.

**Монте-Карло** — метод многократного расчёта со случайными реализациями
неопределённости, дающий распределение исходов вместо единственной траектории.

**Random seed** — значение, фиксирующее последовательность случайных величин и
обеспечивающее воспроизводимость расчёта.

**Коридор P5–P95** — интервал, в который попадает 90 % смоделированных исходов.

**Узкое место** — ограничение, из-за которого деятельность простаивает;
вычисляется по трассе расчёта с количественным обоснованием.

**Происхождение результата** — набор сведений (версия модели, сценарий,
начальное состояние, seed, версия движка, время), позволяющий воспроизвести
расчёт в точности.
