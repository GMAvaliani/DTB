# DTB — Optimization

Исходная постановка (см. «Платформа_2026_06.docx»): состояние `x`, управление
`u`, неопределённость `ζ`, переходная функция `g`, целевая функция `J`;
`x(i−1) = g(x(i), u(i), ζ(i), i)` на неравномерной сетке моментов переключения.
Аналитическое решение уравнения Беллмана возможно лишь в вырожденных случаях —
поэтому платформа реализует **алгоритмический контур поверх имитационного
моделирования и Монте-Карло**.

## Интерфейсы (MVP, реализовано)

- **ObjectiveFunction** — `KPIObjective(kpi_id, direction, quantile=None)`
  (ожидание финального KPI либо его нижний квантиль) и
  `ExpressionObjective("kpi('revenue') - 1e6*(1-prob('g_root'))")` —
  произвольная метрика над ожиданиями KPI, квантилями
  (`kpi_quantile('revenue', 0.1)`), средним NPV (`npv()`) и вероятностями
  достижения целей. Максимизация и минимизация.
- **Критерий сравнения** — среднее по прогонам либо квантиль
  (`quantile=0.1`): осторожный критерий выбирает решения, устойчивые к
  случайности, а не удачные в среднем. Тот же выбор доступен ограничениям.
- **DecisionVariable** — типизированные пути к управляемым параметрам:
  `resource:<id>` (ёмкость), `event_rate:<kind>` (множитель интенсивности),
  `sed_duration:<sed>` (масштаб длительности), `stock:<utility>` (начальный
  запас), `param:<тип>:<id>.<поле>` (произвольный параметр модели),
  `policy:<policy_id>.<порог>` — **порог политики контура управления**:
  условие политики ссылается на него как `threshold('имя')`, а оптимизатор
  подбирает значение.
- **Constraint** — выражения допустимости над оценкой
  (`kpi('service_level') >= 75`, `prob('g_root') >= 0.8`).
- **Оценка кандидата** — Монте-Карло с заданным числом прогонов; все кандидаты
  оцениваются на **общих случайных числах** (один master seed) для честного
  сравнения (variance reduction).

## Оптимизаторы

- `grid_search` — полный перебор декартова произведения значений переменных;
- `random_search` — равномерная выборка для больших пространств;
- `coordinate_search` — покоординатный спуск: переменные перебираются по
  очереди при фиксированных остальных, проход повторяется, пока находится
  улучшение. Нужен для подбора порогов политик, где полный перебор растёт
  экспоненциально, а зависимость почти разделима. Оценки кешируются, обход
  детерминирован (переменные — в порядке задания, значения — в порядке
  решётки, при равенстве счёта удерживается текущее значение), старт — из
  середины решётки. Провенанс содержит трассу проходов;
- `register_optimizer(name, factory)` — plugin-интерфейс для будущих методов:
  динамическое программирование по шагам МП (табличные `J(i,x)`, `u*(i,x)` —
  структура результата уже совместима), stochastic/evolutionary/RL-оптимизация
  (см. ROADMAP).

Результат: таблица оценок (assignment, score, feasible, итоговые KPI,
вероятности целей), лучший допустимый кандидат, provenance (базовый сценарий,
seed, число прогонов, оптимизатор).

## Просмотр вперёд (lookahead)

Оптимизация настраивает параметры **до** прогона. Просмотр вперёд работает
**внутри** прогона: в момент принятия решений политика клонирует состояние,
прогоняет каждого кандидата на заданную глубину и выбирает лучшего по
критерию.

```python
Policy(
    id="pol_invest", name="Развитие", rule="true", action_ref="third_line",
    lookahead=Lookahead(
        horizon=240, objective="npv", runs=3, criterion="quantile",
        quantile=0.25, candidates=["overtime_shift", "second_shift_crew",
                                   "third_line"], min_gain=50_000,
    ),
)
```

* первый прогон-просмотр продолжает ту же случайность, что и основной, —
  это общие случайные числа для всех кандидатов; остальные берут независимые
  субпотоки, выведенные из master seed, поэтому выбор воспроизводим;
* вариант «ничего не делать» оценивается наравне с действиями, а `min_gain`
  задаёт, насколько действие должно быть лучше, чтобы его применили;
* внутри прогона-просмотра просмотр отключён — рекурсия не разрастается;
* критерии: `mean`, `quantile` (осторожный), `worst` (гарантированный),
  `best` (оптимистичный);
* журнал просмотра доступен в результате (`lookahead_log`) и через
  `GET /api/simulations/{id}/lookahead`: видно каждого кандидата, его оценку,
  выбор и выигрыш против «ничего не делать».

Цена просмотра — время: каждая оценка это отдельный короткий прогон. Поэтому
глубина и число прогонов задаются явно, а в демо-модели политика с просмотром
вперёд поставляется выключенной.

## API

`POST /api/optimizations` (фоновая job с прогрессом) / `GET /api/optimizations/{id}` —
см. API.md. UI: экран «Оптимизация».

## Режимы применения (из предметной спецификации)

- **Планирование**: горизонт, начальные условия, целевая функция и критерий →
  оптимизация на всём горизонте.
- **Оперативное управление**: в момент принятия решения (очередной МП) задача
  решается от текущего состояния до конца горизонта — на платформе это
  сценарий с `initial_stock_overrides`/`parameter_overrides`, равными текущему
  состоянию, плюс оптимизация.
- **Стационарный режим**: большой горизонт → задача распределения ресурсов;
  решается теми же переменными `resource:<id>` на длинном горизонте.
