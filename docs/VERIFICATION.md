# DTB — верификация расчёта

Доверие к цифровому двойнику складывается из двух разных вопросов.

1. **Работает ли код?** — отвечают обычные тесты (`tests/unit`,
   `tests/integration`, `tests/e2e`).
2. **Совпадает ли расчёт с теорией?** — отвечает отдельный контур
   верификации (`src/dtb/verification`, `tests/verification`).

Второй контур не проверяет код построчно: он строит обычные модели
предприятия, запускает обычные прогоны движка и сравнивает итог с формулами,
известными из теории массового обслуживания и финансовой математики. Движок
не знает, что его сверяют, — никаких специальных режимов для верификации нет.

## Аналитические эталоны

| Эталон | Что сверяется | Формула |
|---|---|---|
| `mm1` | загрузка, средняя очередь, ожидание, время в системе | ρ = λ/μ, L_q = ρ²/(1−ρ), W_q = ρ/(μ−λ), W = 1/(μ−λ) |
| `mmc` | загрузка и очередь при c каналах | ρ = λ/(cμ), L_q по формуле Эрланга C |
| `dd1` | детерминированная система: пропускная способность, загрузка, отсутствие очереди | ⌊(T−s)/i⌋+1, s/i |
| `discounting` | непрерывное дисконтирование постоянной ставки | ∫₀ᵗ r·e^{−ρt} dt = r(1−e^{−ρT})/ρ |
| `little` | закон Литтла и пропускная способность стационарного режима | L = λ·W, λ_out = λ_in |

Стохастические эталоны (`mm1`, `mmc`, `little`) считаются **по нескольким
независимым повторениям**: оценка длины очереди сама случайна, и по одному
прогону отклоняется от теории на величину статистической погрешности.
Повторения получают сиды, выведенные из основного через SHA-256, поэтому
результат воспроизводим. Допуск задан в долях от эталона и отражает эту
погрешность — он не «подогнан под ответ»: детерминированные эталоны
(`dd1`, `discounting`) сверяются с точностью до 10⁻⁹.

Прогоны длинные (20 000 ч) и с разогревом (2 000 ч): сверяется стационарный
режим, переходный отбрасывается.

Неустойчивая постановка отвергается явно: при λ ≥ μ стационарного режима нет,
и эталон поднимает ошибку вместо того, чтобы сравнивать с бессмысленным
числом.

## Инварианты прогона

Эти проверки выполняются на данных **конкретного** прогона и прикладываются к
нему, поэтому доверие к числам проверяемо, а не декларативно:

* **баланс полезностей** — начальный запас + выпуск − расход = конечный запас
  по каждому виду полезности (для прогона с разогревом проверка
  пропускается: разогрев обнуляет счётчики выпуска и расхода);
* **закон Литтла** — L = λ·W по каждому СЭД с достаточным числом завершений и
  малым хвостом незавершённых экземпляров;
* **учёт ресурсов** — занятые часы не превышают часов ёмкости, загрузка равна
  их отношению;
* **сходимость экономики** — сумма статей и сумма видов начисления равны
  итогу; при положительной ставке дисконтированный доход не больше
  номинального;
* **стоимость управления** — сумма по действиям равна итогу отчёта.

## Как запускать

```bash
# быстрые тесты (контур верификации исключён по умолчанию)
pytest

# контур верификации
pytest -m verification            # или: pytest tests/verification

# из командной строки
dtb verify                                  # все эталоны, 3 повторения
dtb verify --benchmarks mm1,dd1 --replications 5 --seed 42
dtb verify-run demo_baseline                # инварианты на прогоне сценария
```

Код возврата `dtb verify` и `dtb verify-run` равен 3, если хотя бы одна
проверка не прошла, — команду можно ставить в CI как барьер.

## API

```
GET /api/verification/benchmarks[?names=mm1,mmc,dd1,discounting,little
                                 &seed=&horizon=&replications=]
GET /api/simulations/{id}/verification
```

Отчёт содержит по каждой проверке: ожидаемое значение, полученное,
абсолютную погрешность, допуск, итог и пояснение — что именно сверялось.
В интерфейсе отчёт показывается на экране результатов прогона панелью
«Верификация прогона».
