# DTB — Simulation Engine

`dtb.simulation` — независимый, framework-free движок event-driven симуляции в
непрерывном модельном времени (единица — час). Зависит только от `dtb.domain` и
`dtb.common`; тестируется и запускается автономно (rule 4).

## Модель времени: моменты переключения (МП)

Это **не** дискретно-шаговая симуляция. Модельное время скачет от одного МП к
следующему; между соседними МП характер выполнения СЭДов и свойства среды не
меняются. Кандидаты на следующий МП:

1. ближайшее НП-событие каждого потока (пуассоновский поток сэмплируется лениво:
   `t_next = t_prev + Exp(λ)`; плановые — по расписанию; внешние — через адаптер;
   вброшенные сценарием — из его списка);
2. ближайшее завершение выполняемого СЭДа;
3. плановые триггеры СЭД (`at_time`, `recurring`);
4. управляющие воздействия сценария `u(t)` (control actions);
5. истечение временных изменений ёмкости ресурсов (окончание ремонта и т.п.).

Выбирается минимум; часы переводятся (с накоплением интегралов занятости
ресурсов и времени ожидания); все совпавшие по времени наступления
обрабатываются в детерминированном тотальном порядке:

```
expiry ёмкости → завершения СЭД (по seq создания) → НП-события
(по id вида; вброшенные раньше потоковых) → плановые триггеры (по id СЭД)
→ control actions (по порядку списка)
```

После обработки МП: `check_continuation` → `try_start_waiting` → запись
траекторий → цикл.

## Жизненный цикл СЭД-агента

```
created ─→ waiting ─(входы + ресурсы доступны)─→ executing ─→ completed
              ▲                                       │
              └──────────── suspended ←───────────────┘   cancelled / failed
```

- **Создание**: триггеры `on_event` / `on_sed_completed` (с условием и
  count-выражением над payload), `at_time`, `recurring`; эффект `spawn_sed`
  события; `spawn_sed_ids` вероятностной ветви (например, rework после брака).
- **Старт**: проверяются `max_concurrent`, `start_condition`, достаточность
  входных полезностей и свободной ёмкости ресурсов. Порядок конкуренции —
  `(priority, seq)`, проходы до фикспойнта. Входы **потребляются при старте**,
  ресурсы аллоцируются, длительность сэмплируется (fixed | uniform | triangular
  | normal | lognormal | exponential) из субпотока данного СЭДа.
- **Завершение**: выбирается вероятностная ветвь исхода, выходные полезности
  **производятся при завершении**, ресурсы освобождаются, срабатывает внутреннее
  событие завершения → цепочки `on_sed_completed`.
- **Приостановка**: на каждом МП для выполняемых проверяются
  `continuation_condition` и достаточность ёмкости (события могли её отнять —
  отказ оборудования, увольнение). Нарушители приостанавливаются LIFO (последний
  стартовавший — первым), возвращаются в waiting с **остатком длительности**;
  входы повторно не потребляются, при рестарте длительность не пересэмплируется.

## Режимы выполнения СЭД

- **Mode A (агрегированный)** — потребление входов, заданная (стохастическая)
  длительность, производство выходов; основной способ быстрого моделирования.
- **Mode B (внешняя модель)** — `external_model.uri` вызывается через адаптер
  (`http` | `callable`); внешняя модель возвращает длительность и, опционально,
  выходы/ветвь. Движку передаётся детерминированный derived seed, чтобы внешняя
  модель могла быть воспроизводимой. Недоступность внешней модели **честно
  фейлит прогон** (никаких тихих фолбэков). Потоки событий тоже могут быть
  внешними (`stream.kind = external`).

## Эффекты событий

`spawn_sed`, `add_utility` / `remove_utility` (количество — safe-выражение над
payload и состоянием), `resource_capacity_delta` (временная — с длительностью, или
постоянная), `set_parameter` (пути вида `event_kind:<id>.stream.rate_per_hour` —
изменение интенсивности потока применяется немедленно с инвалидированием
сэмплера), `cancel_sed_instances`. Условные эффекты — через `condition`.

## Детерминизм

Один master seed; субпотоки выводятся SHA-256 от `(seed, назначение, id)`
(`dtb.common.seeding`): поток каждого вида событий, длительности каждого СЭДа,
выбор ветвей каждого СЭДа, прогоны Монте-Карло, random search. Пауза/отмена —
кооперативные чекпоинты, не трогающие RNG. Инвариант закреплён тестами:
`SimulationResult.content_digest()` идентичен при идентичных (model, scenario,
initial state, seed).

## Результат

`SimulationResult`: полный **provenance** (enterprise, model version + hash,
scenario id + version, initial-state hash, seed, horizon, версия движка,
timestamp), KPI/сток/пул-траектории (сэмплируются по МП с прореживанием),
журнал событий (с капом), статистика СЭДов (created/started/completed/
suspensions/waiting_hours/`blocked_hours` по причинам/queue_peak), статистика
ресурсов (utilization = ∫busy/∫capacity, пики), итоги полезностей, достижение
целей (по значению KPI на дедлайне), метрики исполнения (НП-события, МП,
wall-time, размеры пулов).

## Наблюдаемость и управление

`progress_cb` получает прогресс каждые N МП (время, события, размеры пулов);
`SimControl` даёт pause/resume/cancel (используется API-джобами и SSE).
Защита от разгона: `max_events` для НП-событий и 4× лимит на МП (страховка от
циклов нулевой длительности; валидация ловит их заранее).

## Ограничения MVP (не скрываются)

- Календарь `24x7`: рабочие календари/смены — в ROADMAP.
- Ёмкость ресурса, «выключенная» до 0 постоянным эффектом, не восстанавливается
  сама — верните её событием/эффектом.
- `utilization` считается по базовой+временной ёмкости на момент интегрирования.
