# Описание программного комплекса DTB

**Цифровой двойник деятельности предприятия** — объединённая модель: платформа
DTB, дополненная механиками референсного движка-имитатора (контур управления,
наблюдения, экономика, верификация, режимы работы, просмотр вперёд, контракт
стыковки).

---

## 1. Назначение и общее устройство

### 1.1. Назначение

Комплекс предназначен для того, чтобы **заранее, на модели, проверить
управленческое решение** — прежде чем принимать его на реальном предприятии.
Типовые вопросы, на которые он отвечает:

- достигнет ли предприятие цели (выручки, уровня сервиса, объёма) при
  текущей организации работы и с какой вероятностью;
- где узкое место — какой ресурс, какая операция тормозят результат;
- что даст изменение: дополнительная линия, вторая смена, новый поставщик,
  рост спроса, другие правила реагирования;
- окупится ли решение с учётом стоимости денег во времени (NPV);
- насколько вывод устойчив, не является ли он следствием удачного случая.

### 1.2. Как устроена модель

Предприятие описывается в терминах методологии комплексной деятельности:

| Понятие | Что это в модели |
|---|---|
| **СЭД** — структурный элемент деятельности | операция: что потребляет, что производит, какие ресурсы занимает, сколько длится, что её запускает |
| **Полезность** | то, что создаётся и потребляется: заказ, материал, изделие, деньги, обученный сотрудник |
| **Ресурс** | то, что занимается на время операции и освобождается: люди, линии, транспорт |
| **НП-событие** | событие внешней среды: поступление заказа, отказ оборудования, поставка |
| **Цель и KPI** | что предприятие хочет получить и как это измеряется |
| **Контур управления** | кто, когда и по какому правилу принимает решения внутри модели |

### 1.3. Как идёт расчёт

Время в модели **непрерывное**, но двигается скачками — от одного **момента
переключения (МП)** к следующему. МП наступает, когда что-то меняется:
пришло событие, завершилась операция, началась смена, вступило в силу решение.

В каждом МП движок:

1. обрабатывает все события этого момента в строгом порядке;
2. запускает ожидающие СЭД, для которых хватает входов и ресурсов;
3. проверяет, не нарушены ли условия продолжения у выполняющихся СЭД;
4. если это ещё и **момент принятия решений (МР)** — вызывает политики,
   которые читают *наблюдаемое* состояние и применяют управляющие действия;
5. накапливает статистику и экономику на интервале до следующего МП.

Большинство МП решения не требуют. Решения принимаются только в МР — по
регламенту (раз в смену, раз в неделю), по событию (отказ оборудования) или по
сторожевому условию (очередь выросла выше порога). Так модель воспроизводит
реальный ритм управления, а не «идеального диспетчера», реагирующего на всё
мгновенно.

### 1.4. Случайность и воспроизводимость

Длительности, потоки событий, исходы операций, успех управленческих действий и
погрешности наблюдений — случайные. Все они порождаются из одного **master
seed** через независимые подпотоки. Поэтому:

- одинаковые модель, сценарий и seed дают **побитово одинаковый** результат;
- два сценария, посчитанные на одном seed, сравниваются на **общих случайных
  числах** — разница между ними обусловлена решением, а не везением.

## 2. Состав комплекса

### 2.1. Программные модули

| Модуль | Назначение |
|---|---|
| `domain` | описание модели: СЭД, полезности, ресурсы, события, цели, KPI, контур управления, экономика, календари |
| `simulation` | движок расчёта: МП и МР, политики, наблюдения, экономика, разогрев, очереди, прерывания, просмотр вперёд |
| `analysis` | Монте-Карло, прогноз «план / факт / прогноз», узкие места, сравнение сценариев с парными разностями |
| `optimization` | подбор решений: полный перебор, случайный и покоординатный поиск, критерий по среднему или квантилю |
| `validation` | проверка модели перед расчётом и оценка качества данных |
| `verification` | сверка движка с аналитическими эталонами и проверка инвариантов каждого прогона |
| `graph` | граф знаний: связи между сущностями, анализ влияния и зависимостей |
| `integration` | импорт и экспорт Excel, CSV, JSON; коннекторы к ERP |
| `interop` | контракт стыковки с другими движками имитации |
| `persistence` | хранение моделей, версий, сценариев, результатов, журнала изменений |
| `api` + `frontend` | веб-интерфейс и REST API |

### 2.2. Экраны веб-интерфейса

Предприятия · Модель предприятия · Дерево целей · СЭД / Полезности ·
События (НП) · Оргструктура · Ресурсы и оборудование · ERP-объекты и связи ·
Сценарии · Симуляция · Результаты и таймлайн · Прогноз · Сравнение сценариев ·
Оптимизация · Граф знаний · AI-ассистент · Импорт / Экспорт · Версии модели ·
Журнал изменений.

### 2.3. Командная строка

| Команда | Что делает |
|---|---|
| `dtb serve` | запустить веб-интерфейс и API (http://localhost:8000) |
| `dtb demo` | создать демонстрационное предприятие «Демо-Завод» |
| `dtb simulate <сценарий> [--runs N] [--seed S]` | прогон или серия Монте-Карло |
| `dtb validate <предприятие>` | проверить модель |
| `dtb export-template <файл.xlsx>` | выгрузить пустой шаблон книги |
| `dtb verify` | сверить движок с аналитическими эталонами |
| `dtb verify-run <сценарий>` | проверить инварианты на прогоне |
| `dtb certify <предприятие> [--uri URL]` | проверить движок на соответствие контракту стыковки |

## 3. Загрузка модели

Модель можно создать четырьмя способами:

1. **Из Excel-книги** — основной способ для нового предприятия (раздел 5).
2. **В веб-интерфейсе** — экранами «СЭД / Полезности», «Ресурсы», «События» и
   т.д.; удобно для правок.
3. **Из JSON** — полный снимок модели, например выгрузка из другой установки.
4. **Из ERP** — коннектор подтягивает сотрудников, оборудование, остатки.

### 3.1. Загрузка Excel-книги

1. Экран **«Предприятия»** → создайте предприятие: идентификатор (латиницей,
   например `workshop`), название, горизонт планирования в часах (месяц —
   720).
2. Выберите его в списке слева вверху.
3. Экран **«Импорт / Экспорт»** → «Импорт Excel (все листы)» → выберите файл →
   «Импортировать».
4. Платформа покажет отчёт: сколько сущностей создано и обновлено, какие
   строки отвергнуты и почему (с номером строки).
5. Экран **«Модель предприятия»** → блок **«Валидация»**: критические ошибки
   нужно исправить — с ними расчёт не запустится.

Листы читаются в правильном порядке независимо от их порядка в книге.
Повторная загрузка той же книги **обновляет** сущности с теми же `id`, а не
дублирует их. Названия листов можно писать по-русски: «Полезности», «СЭД»,
«Ресурсы», «События», «Политики», «Календари», «Экономика» и т.д.

### 3.2. Пустой шаблон

```bash
dtb export-template шаблон.xlsx
```

или на экране «Импорт / Экспорт» → «Скачать шаблон». Шаблон содержит все листы
с правильными заголовками. Выгрузка существующей модели (кнопка «Экспорт
Excel») даёт заполненную книгу — лучший образец для начала.

## 4. Смысл основных столбцов

Общие правила:

- `id` — уникальный идентификатор латиницей, без пробелов: на него ссылаются
  другие листы. `name` — человекочитаемое название.
- Время — **в часах** модельного времени от начала прогона.
- Пустая ячейка означает значение по умолчанию.
- Списки в одной ячейке разделяются точкой с запятой: `a; b; c`.

### 4.1. Лист `utility_types` — полезности

| Столбец | Смысл |
|---|---|
| `kind` | вид: `product`, `material`, `raw_material`, `component`, `money`, `information`, `work`, `service`, `energy`, `trained_employee`, `moved_stock`, `other` |
| `unit` | единица измерения: шт, кг, руб, чел |

### 4.2. Лист `seds` — структурные элементы деятельности

| Столбец | Смысл | Пример |
|---|---|---|
| `inputs` | что потребляется при запуске | `order:1; steel:2.5` |
| `outputs` | что производится при завершении | `product:1` |
| `resources` | какие ресурсы заняты на время выполнения | `line:1; worker:2` |
| `duration` | длительность, ч | см. ниже |
| `triggers` | что запускает СЭД | см. ниже |
| `goal_id` | какую цель реализует | `g_revenue` |
| `parent_id` | вышестоящий СЭД (иерархия) | `production` |
| `priority` | меньше — раньше при конкуренции | `10` |
| `max_concurrent` | сколько экземпляров одновременно | `3` |
| `start_condition` | дополнительное условие запуска | `stock('money') > 0` |
| `continuation_condition` | условие продолжения; если нарушено — приостановка | |
| `interruption_mode` | что делать при прерывании: `resume`, `wait`, `restart`, `fail` | `restart` |
| `branches` | вероятностные исходы (JSON) | брак 5% с отправкой на переделку |

**Длительность:**

| Запись | Значение |
|---|---|
| `fixed:4` | ровно 4 ч |
| `uniform:2..6` | равномерно от 2 до 6 ч |
| `triangular:2..6@4` | треугольное: от 2 до 6, наиболее вероятно 4 |
| `normal:5,1` | нормальное: среднее 5, СКО 1 |
| `exponential:5` | экспоненциальное со средним 5 |
| `lognormal:1,0.5` | логнормальное |

**Триггеры:**

| Запись | Значение |
|---|---|
| `on_event:order_in` | при каждом событии `order_in` |
| `on_sed_completed:sales` | после каждого завершения СЭД `sales` |
| `at_time:100` | однократно в момент 100 ч |
| `recurring:24@8` | каждые 24 ч, начиная с 8-го часа |

**Режимы прерывания** — что происходит с операцией, прерванной концом смены,
отказом оборудования или нарушением условия:

| Режим | Поведение |
|---|---|
| `resume` | наработка сохраняется, операция возвращается в общую очередь (по умолчанию) |
| `wait` | наработка сохраняется, операция удерживает место в очереди и продолжается первой |
| `restart` | наработка теряется, операция начинается заново |
| `fail` | операция снимается как отказ |

### 4.3. Лист `resources` — ресурсы

| Столбец | Смысл |
|---|---|
| `kind` | `personnel`, `equipment`, `facility`, `vehicle`, `financial`, `energy`, `other` |
| `capacity` | сколько единиц одновременно доступно |
| `queue_discipline` | порядок обслуживания очереди: `priority` (по приоритету СЭД, по умолчанию), `fifo`, `lifo`, `spt` (сначала короткие) |
| `calendar_ref` | график работы с листа `calendars`; вне смены ресурс недоступен |
| `cost_per_hour` | справочная стоимость часа (в экономику не входит; для экономики — лист `economic_items`) |

### 4.4. Лист `event_kinds` — события внешней среды

| Столбец | Смысл |
|---|---|
| `category` | `external` (внешняя среда), `internal` (внутри предприятия: отказы, увольнения), `planned` (плановые: обслуживание), `regulatory`, `uncertain` |
| `stream_kind` | `poisson` — случайный поток; `scheduled` — в заданные моменты и/или регулярно; `external` — от внешней модели по URI; `none` — только по сценарию |
| `rate_per_hour` | интенсивность пуассоновского потока: 0,4 — в среднем 0,4 события в час |
| `times` | моменты для `scheduled`: `10; 40; 200` |
| `interval`, `start` | период и начало регулярного потока `scheduled` |
| `effects` | что событие делает (JSON): добавить полезность, изменить ёмкость ресурса, запустить СЭД, изменить параметр |

Пример `effects` — заказ пополняет запас полезности `order`:
```json
[{"kind": "add_utility", "utility_type_id": "order", "quantity_expression": "1"}]
```

Пример — отказ снимает одну линию на 8 часов:
```json
[{"kind": "resource_capacity_delta", "resource_id": "line", "delta": -1, "duration": 8}]
```

### 4.5. Лист `kpis` — показатели

`expression` — формула над состоянием модели. Доступные функции:

| Функция | Значение |
|---|---|
| `produced('money')` | сколько полезности произведено |
| `consumed('steel')` | сколько потреблено |
| `stock('order')` | текущий запас |
| `completed('sale')`, `started('sale')` | число завершённых / запущенных экземпляров СЭД |
| `waiting_count('sale')`, `executing_count('sale')` | в очереди / в работе сейчас |
| `utilization('line')` | загрузка ресурса от 0 до 1 |
| `events('order_in')` | сколько событий произошло |
| `kpi('revenue')` | значение другого KPI |
| `t()` | текущее модельное время |

Допустимы арифметика, сравнения, `and`, `or`, `max`, `min`, `abs`, `round`.

### 4.6. Лист `goals` — цели

| Столбец | Смысл | Пример |
|---|---|---|
| `targets` | целевые значения KPI | `revenue:>=:1000000` или `revenue:>=:1000000:720` (с крайним сроком) |
| `parent_id` | вышестоящая цель | `g_root` |
| `sed_ids` | какие СЭД её реализуют | `production; sale` |

### 4.7. Листы контура управления

**`subjects`** — кто принимает решения: `authority_level` (уровень полномочий),
`role_ref` (роль в системе: `viewer`, `editor`, `admin`).

**`control_actions`** — каталог управленческих действий:

| Столбец | Смысл |
|---|---|
| `loop` | контур: `regulation` (быстрый), `organization` (средний), `development` (длинный) |
| `effect` | что действие делает (JSON, как в событиях) |
| `activation_delay` | через сколько часов после решения вступает в силу |
| `term` | срок действия, ч; по истечении эффект откатывается |
| `reversible` | можно ли откатить; `0` — эффект навсегда |
| `one_time_cost`, `recurring_cost` | разовая стоимость и стоимость в час |
| `success_probability` | вероятность, что действие удастся |
| `min_authority_level` | какой уровень полномочий нужен; без него действие отклоняется |

**`policies`** — правила выбора действия:

| Столбец | Смысл | Пример |
|---|---|---|
| `rule` | условие | `waiting_count('service') >= threshold('q')` |
| `action_ref` | какое действие применить | `helper` |
| `thresholds` | пороги, на которые ссылается условие | `q:4` |
| `rules` | несколько ветвей сразу | `stock('m') < 5 -> buy @ 10; true -> hold` |
| `cooldown_hours` | не срабатывать чаще, чем раз в N часов | `48` |
| `lookahead` | просмотр вперёд (JSON): сравнить варианты короткими прогонами | `{"horizon": 72, "objective": "npv"}` |

**`decision_points`** — когда вызываются политики:

| `kind` | Когда | Нужные столбцы |
|---|---|---|
| `timer` | по регламенту | `timer_period`, `timer_start` |
| `event` | при событии | `event_ref` |
| `watchdog` | когда условие впервые стало истинным | `watchdog_condition` |

`policy_ref` — какую политику вызывать (пусто — все подходящие).

**`observations`** — что политика видит и с каким качеством:

| Столбец | Смысл |
|---|---|
| `target_kind`, `target_ref` | что наблюдается: `resource` / `sed` / `utility_type` / `kpi` и его `id` |
| `period` | как часто снимается, ч |
| `delay` | через сколько часов становится известно |
| `relative_error` | относительная погрешность: 0,1 — ±10% |
| `estimator` | как строится оценка: `last`, `smooth`, `extrapolate` |
| `mode` | `twin` — политика видит оценку; `pure_simulation` — истину |

### 4.8. Лист `calendars` — графики работы

| Столбец | Пример | Смысл |
|---|---|---|
| `shifts` | `пн-пт:6-14; пн-пт:14-22; сб:8-14@0.5` | смены: дни, часы, доля ёмкости |
| `exceptions` | `336-360; 500-508:работа` | плановая остановка либо дополнительная смена |

Ночная смена задаётся двумя интервалами: `22-24` и `0-6`.

### 4.9. Листы экономики

**`economics`** (одна строка): `currency`, `discount_rate_annual` (0,15 = 15%
годовых), `warmup_hours` (разогрев), `include_control_costs`.

**`economic_items`** — статьи начисления:

| Столбец | Смысл |
|---|---|
| `kind` | `rate` — ставка в час; `one_time` — за событие; `terminal` — остаточная стоимость на конце горизонта |
| `basis` | база: `constant`, `resource_capacity` (номинальная ёмкость), `resource_available` (по графику смен), `resource_busy` (занятость), `utility_stock` (хранение), `wip`, `queue`, `sed_completed`, `sed_started`, `utility_produced`, `utility_consumed`, `expression` |
| `direction` | `income` или `expense` |
| `ref` | к чему относится база: ресурс, полезность или СЭД |
| `rate` | ставка: руб/ч для `rate`, руб за единицу для `one_time` |
| `article` | статья в отчёте: «выручка», «ФОТ», «материалы» |

### 4.10. Прочие листы

`plans`, `actuals` — плановые и фактические значения KPI во времени (для
прогноза «план / факт / прогноз»). `org_units`, `employees`, `equipment` —
оргструктура и оборудование. `initial_state` — начальные запасы полезностей.
`erp_objects`, `erp_mappings` — связь с ERP. `links`, `gap_types` — заготовки
под исследование связей и разрывов (хранятся, в расчёте не участвуют).

## 5. Порядок создания книги для нового предприятия

Идите от результата к ресурсам, а не наоборот. Каждый шаг проверяйте загрузкой
и валидацией — так ошибка обнаруживается сразу, а не в конце.

1. **Цель и показатели.** Что предприятие должно получить и как это измерить?
   Заполните `kpis` и `goals`. Пример: «выручка за месяц не ниже 1 млн».
2. **Полезности.** Перечислите, что создаётся и потребляется на пути к цели:
   заказ → контракт → изделие → деньги. Лист `utility_types`.
3. **СЭД.** Для каждого шага цепочки — операция: что берёт на входе, что
   отдаёт на выходе, сколько длится. Лист `seds`. Выход одного СЭД должен быть
   входом следующего — иначе цепочка разорвётся.
4. **Запуск цепочки.** Первый СЭД запускается событием (`on_event`),
   последующие — завершением предыдущего (`on_sed_completed`). Лист
   `event_kinds` с интенсивностью внешнего потока.
5. **Ресурсы.** Кто и что выполняет операции; сколько их. Лист `resources`,
   столбец `resources` в `seds`.
6. **Начальное состояние.** Запасы на старте — лист `initial_state`.
7. **Первая проверка.** Загрузите книгу, исправьте ошибки валидации, сделайте
   один прогон. Убедитесь, что цепочка доходит до конца: KPI не нулевые.
8. **Режимы работы.** Если ресурсы работают не круглосуточно — `calendars` и
   `calendar_ref` у ресурсов. Пересчитайте ёмкость: при двух сменах из пяти
   дней ресурс доступен меньше половины времени.
9. **Экономика.** Ставки содержания и оплаты труда, доходы, материалы,
   остаточная стоимость — листы `economic_items` и `economics`.
10. **Контур управления** — если нужно моделировать решения внутри периода:
    действия, политики, моменты решений, наблюдения.
11. **План и факт** — для сравнения прогноза с планом: `plans`, `actuals`.
12. **Калибровка.** Сравните результат базового прогона с известными фактами
    (выручка за прошлый месяц, средняя загрузка, типичная очередь). Расхождение
    больше 10–15% — повод уточнить длительности и интенсивности до
    экспериментов.

## 6. Пример А: простейшее предприятие из одного СЭДа

Готовая книга — `examples/example_A_one_sed.xlsx`; её пересобирает скрипт
`examples/build_example_a.py`.

### 6.1. Постановка

Мастерская: один мастер выполняет заказы. Заказы приходят случайно, в среднем
0,4 в час. Выполнение занимает от 1 до 3 часов, чаще всего 2. Каждый заказ
приносит 5 000 руб. Мастеру платят 400 руб/ч. Цель — выручка не ниже 1 млн руб
за месяц (720 ч).

### 6.2. Книга

**`utility_types`**

| id | name | kind | unit |
|---|---|---|---|
| order | Заказ | information | шт |
| money | Денежные средства | money | руб |

**`resources`**

| id | name | kind | capacity | unit |
|---|---|---|---|---|
| master | Мастер | personnel | 1 | чел |

**`event_kinds`**

| id | name | category | stream_kind | rate_per_hour | effects |
|---|---|---|---|---|---|
| order_in | Поступил заказ | external | poisson | 0.4 | `[{"kind":"add_utility","utility_type_id":"order","quantity_expression":"1"}]` |

**`seds`**

| id | name | inputs | outputs | resources | duration | triggers |
|---|---|---|---|---|---|---|
| service | Выполнение заказа | order:1 | money:5000 | master:1 | triangular:1..3@2 | on_event:order_in |

**`kpis`**

| id | name | expression | unit |
|---|---|---|---|
| revenue | Выручка | `produced('money')` | руб |
| done | Выполнено заказов | `completed('service')` | шт |
| load | Загрузка мастера | `100 * utilization('master')` | % |
| queue | Заказов в очереди | `waiting_count('service')` | шт |

**`goals`**

| id | name | targets | sed_ids |
|---|---|---|---|
| g_revenue | Выручка за месяц | revenue:>=:1000000 | service |

**`economic_items`**

| id | name | article | kind | basis | direction | ref | rate |
|---|---|---|---|---|---|---|---|
| income | Оплата заказов | выручка | one_time | utility_produced | income | money | 1 |
| wage | Оплата мастера | фонд оплаты труда | rate | resource_capacity | expense | master | 400 |

**`economics`**

| currency | discount_rate_annual | warmup_hours |
|---|---|---|
| руб | 0.15 | 0 |

### 6.3. Как это работает

1. Событие `order_in` происходит в случайные моменты и добавляет одну единицу
   полезности `order`.
2. То же событие создаёт экземпляр СЭД `service` — он встаёт в очередь.
3. Если мастер свободен и заказ есть, экземпляр запускается: заказ
   списывается, мастер занят на случайное время от 1 до 3 ч.
4. По завершении мастер освобождается, появляется 5 000 руб, а экономика
   начисляет доход.
5. Всё это время экономика начисляет 400 руб/ч на оплату мастера.

### 6.4. Результат (720 ч, seed 1)

| Показатель | Значение |
|---|---|
| Поступило заказов | 278 |
| Выполнено | 277 |
| Выручка | 1 385 000 руб — цель достигнута |
| Загрузка мастера | 75,6% |
| Среднее ожидание заказа | 4,9 ч |
| NPV (15% годовых) | 1 090 137 руб |
| Проверка инвариантов | пройдена |

По 20 прогонам Монте-Карло: выручка в среднем 1,40 млн руб, 90% прогонов —
от 1,33 до 1,47 млн, вероятность достижения цели — 100%.

**Сверка с теорией.** Загрузка ρ = интенсивность × средняя длительность =
0,4 × 2 = 0,8. Модель даёт 0,76 на одном прогоне — в пределах случайного
разброса. Это быстрый способ убедиться, что модель собрана верно.

## 7. Как проводить эксперименты

Эксперимент — это **сценарий**: изменение относительно базовой модели, которое
не трогает саму модель. Модель остаётся одна, сценариев — сколько угодно.

### 7.1. Что можно менять в сценарии

| Что | Где в сценарии | Пример |
|---|---|---|
| интенсивность событий | множитель потока | рост спроса на 50%: `order_in × 1.5` |
| ёмкость ресурсов | переопределение ёмкости | два мастера вместо одного |
| длительности операций | масштаб длительности СЭД | ускорение на 20%: × 0,8 |
| начальные запасы | переопределение запаса | |
| любой параметр модели | путь параметра | `policy:pol_queue.thresholds.q = 6` |
| управляющие воздействия во времени | список действий | в момент 240 ч — маркетинговая кампания |
| режим наблюдений | `twin` или `pure_simulation` | цена неполноты информации |
| разогрев и дисконт | `warmup_hours`, `discount_rate_annual` | |

Сценарий создаётся на экране **«Сценарии»**: кнопка «What-if» у базового
сценария.

### 7.2. Пример: рост спроса в мастерской

Тот же Пример А, 20 прогонов Монте-Карло на одном seed:

| Сценарий | Выручка, млн руб | Очередь на конец месяца | NPV, млн руб |
|---|---|---|---|
| База (0,4 заказа/ч, 1 мастер) | 1,40 | 0 | — |
| Спрос +50% | 1,78 | **69 заказов** | 1,49 |
| Спрос +50%, 2 мастера | 2,13 | 0,6 | 1,54 |
| Спрос +50%, политика «помощник при очереди ≥ 4» | 2,11 | 3,2 | 1,53 |

Чтение результата:

- При росте спроса загрузка одного мастера становится 0,6 × 2 = 1,2 — больше
  единицы. Очередь растёт без предела: система неустойчива. Модель это
  показывает, а цифра выручки сама по себе нет — поэтому смотрите на очередь.
- Второй постоянный мастер решает проблему полностью.
- Политика «нанимать помощника на 48 ч, когда в очереди 4 заказа и больше»
  даёт почти ту же выручку и почти тот же NPV при меньшем постоянном штате.
  Это пример решения, которое невозможно оценить без контура управления в
  модели.

Политика задаётся тремя строками книги:

**`control_actions`**: `helper` — эффект «+1 к ёмкости мастера», срок 48 ч,
разовая стоимость 3 000 руб, 350 руб/ч.
**`policies`**: `pol_queue` — условие `waiting_count('service') >= threshold('q')`,
действие `helper`, порог `q:4`, не чаще раза в 48 ч.
**`decision_points`**: `dp_day` — `timer`, период 24 ч (ежедневная планёрка).

### 7.3. Инструменты эксперимента

- **Одиночный прогон** — экран «Симуляция», вид «один прогон». Чтобы
  посмотреть траекторию, журнал событий, решения политик.
- **Монте-Карло** — тот же экран, 20–50 прогонов. Для любых выводов: один
  прогон — это один случай, а не закономерность.
- **Сравнение** — экран «Сравнение сценариев». Выберите базу и вариант.
  Смотрите таблицу **парных разностей**: если 95%-доверительный интервал не
  содержит ноль, различие значимо.
- **Прогноз** — экран «Прогноз»: факт, план и прогноз с доверительной
  полосой, вероятность достижения каждой цели.
- **Оптимизация** — экран «Оптимизация»: задайте переменные (ёмкость ресурса,
  порог политики `policy:pol_queue.q`), целевую функцию (KPI или `npv()`),
  ограничения. Метод — полный перебор либо покоординатный поиск. Критерий
  «квантиль 0,1» выбирает решение, устойчивое к неудачным случаям.
- **Просмотр вперёд** — для политики, которой нужно сравнивать варианты в
  момент решения: она прогоняет каждый вариант вперёд из текущего состояния и
  выбирает лучший.
- **Цена неполноты информации** — сценарий с `observation_mode =
  pure_simulation` против базового: разница — это сколько стоит запаздывание
  и погрешность данных, на которых принимаются решения.

## 8. Порядок работы

Рекомендуемый цикл — от модели к решению:

1. **Собрать модель** — книга Excel (раздел 5) или интерфейс.
2. **Проверить** — экран «Модель предприятия» → валидация. Критические
   ошибки исправить; предупреждения прочитать.
3. **Сохранить версию** — экран «Версии модели». Любой результат потом можно
   соотнести с версией модели, на которой он получен.
4. **Базовый прогон** — один прогон, затем Монте-Карло. Проверить
   правдоподобие (раздел 9) и калибровку по фактам.
5. **Найти узкое место** — экран «Результаты»: блок «Узкие места», загрузка
   ресурсов, очереди; «Граф знаний» → анализ влияния ресурса на цели.
6. **Сформулировать варианты** — сценарии what-if: что изменить и насколько.
7. **Сравнить** — экран «Сравнение сценариев», парные разности, NPV.
8. **Подобрать параметры** — экран «Оптимизация», если вариантов много.
9. **Проверить устойчивость** — другой seed, критерий по квантилю, сценарий
   стресса (рост отказов, падение спроса).
10. **Зафиксировать** — версия модели, сценарий и прогон с provenance (seed,
    хеш модели, версия движка) образуют воспроизводимое обоснование решения.

После внедрения решения внесите фактические данные (`actuals`) и сравните с
прогнозом — так модель уточняется от цикла к циклу.

## 9. Что делать с результатом, который выглядит неправдоподобно

Неправдоподобный результат почти всегда означает ошибку в модели, а не в
движке: корректность движка подтверждается сверкой с теорией
(`dtb verify`). Ищите в таком порядке.

### 9.1. Проверить, что расчёт был корректен технически

1. Экран «Результаты» → блок **«Верификация прогона»**. Нарушение баланса
   полезностей или закона Литтла — признак ошибки в описании модели.
2. Экран «Модель предприятия» → **валидация**: прочитайте и предупреждения —
   «СЭД не запускается», «событие ни на что не влияет», «политика никогда не
   вызывается».
3. Статус прогона: `truncated` значит, что достигнут лимит событий — модель
   породила лавину (цикл СЭД без выхода, слишком высокая интенсивность).

### 9.2. Типовые симптомы и причины

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| KPI равен нулю | цепочка разорвана: выход одного СЭД не совпадает со входом следующего | `id` полезностей в `inputs`/`outputs`; в журнале событий — какие СЭД запускались |
| очередь растёт до конца прогона | загрузка ресурса ≥ 1: спрос больше мощности | интенсивность × средняя длительность ÷ ёмкость; календарь смен |
| ресурс загружен на 0% | СЭД не запрашивает его либо не запускается | столбец `resources` в `seds`; блок «Узкие места» |
| выручка в разы выше факта | лишний ноль в `outputs` или `rate_per_hour`; события в час вместо дня | единицы: время — в часах |
| результат одинаков во всех прогонах | в модели нет случайности или одинаковый seed | длительности `fixed`, поток `scheduled`; seed в Монте-Карло |
| огромный разброс между прогонами | система близка к неустойчивости (загрузка ~0,95) | увеличьте число прогонов; смотрите квантили, а не среднее |
| ничего не работает ночью и в выходные | календарь смен у ресурса | `calendar_ref`, «Вне смен, ч» в таблице ресурсов |
| политика не срабатывает | нет момента принятия решений; условие не выполняется в моменты решения; антидребезг | лист `decision_points`; панель «Контур управления»; журнал политик |
| действие политики не применяется | не хватает полномочий; неудача по вероятности успеха | «Отклонённые действия» в панели контура |
| решение принимается «не вовремя» | политика видит запаздывающую или сглаженную оценку | лист `observations`: `delay`, `estimator`; сравните с `pure_simulation` |
| NPV сильно отрицательный | ставки начисляются круглосуточно, а работа идёт по сменам | `resource_capacity` против `resource_available` в `economic_items` |
| NPV не меняется при разных решениях | разовые статьи без дохода; экономика не задана | лист `economic_items`, статья с `direction = income` |
| итоги после разогрева меньше ожидаемых | разогрев отбрасывает начало периода | `warmup_hours`: итог измеряется от его конца |

### 9.3. Приёмы отладки

- **Упростить.** Отключите политики (`enabled = 0`), календари, отказы —
  верните модель к ядру и включайте элементы по одному, пока не найдётся тот,
  что даёт аномалию.
- **Проверить на пальцах.** Для каждого ресурса посчитайте загрузку
  вручную: поток в час × средняя длительность ÷ ёмкость. Если модель даёт
  заметно другое — ошибка в описании.
- **Смотреть журнал.** Экран «Результаты» → «Журнал событий»: видно, какой
  СЭД стартовал, почему ждал (`blocked`: нехватка полезности или ресурса),
  когда завершился.
- **Короткий горизонт.** Прогон на 24–48 часов с журналом проще прочитать
  целиком.
- **Сравнить с другим seed.** Если аномалия только на одном seed — это
  редкий случай, а не закономерность; судите по Монте-Карло.
- **Граф знаний.** Анализ зависимостей цели показывает, какие ресурсы и
  события на неё влияют. Если ожидаемой связи нет — её нет и в модели.
- **Сверить движок.** `dtb verify` — если эталоны проходят, движок считает
  верно, и искать нужно в модели.

### 9.4. Когда результат правдоподобен, но удивляет

Модель может показать то, чего не ожидали, и оказаться права. Прежде чем
отвергнуть результат:

1. найдите в журнале **механизм** — цепочку событий, которая к нему привела;
2. проверьте, воспроизводится ли он на 20–50 прогонах;
3. проверьте, значима ли разница по парным разностям.

Если механизм понятен, воспроизводим и значим — это и есть ценность двойника:
он показал эффект, который не виден из таблиц.
